# Project Risk Register
| **Risk ID** | **Risk Description** | **Possible Cause** | **Probability** | **Impact** | **Mitigation / Response Strategy** |
|---|---|---|---|---|---|
| R1 | Requirements for the system might change or not be fully clear while we are working on it | Stakeholder needs were not gathered in enough detail at the start, or expectations change as the project goes on | Medium | High | Review requirements together as a team early on and keep the scope documented clearly, so new requests are discussed before being added |
| R2 | Connecting our system to the pharmacy's inventory system might cause problems | We may not have access to a real inventory system, or data formats might not match what we expect | Medium | High | Use a sample/mock inventory dataset to build and test with first, and design our code so the real inventory system can be connected later without rewriting everything |
| R3 | A team member might not be available or might miss a deadline | Exams, other coursework, personal circumstances, or workload not divided evenly | High | Medium | Split tasks clearly between team members with extra time built in, and check in weekly so we notice early if someone is falling behind |
| R4 | The team might not be familiar enough with the technology chosen to build the system | We decide to use a framework or tool none of us have real experience with | Medium | Medium | Pick tools we already have some experience with; if not, spend early time learning/practicing before building actual features |
| R5 | Patient and prescription data could be exposed or handled insecurely | Weak login/access control, or sensitive data not being protected properly | Low | High | Set up basic login and access permissions, avoid storing more patient data than necessary, and review our data handling before submitting |
